Open research project for reverse engineering 10th generation Honda Civic infotainment systems (Android-based, NVIDIA Tegra 3).

## What it is

An open research project — documentation plus a monorepo of host-side tools — for reverse engineering the infotainment headunits of 10th-generation Honda Civics (model years 2016–2021). The headunits are Mitsubishi Electric units running Android 4.2.2 on an NVIDIA Tegra 3 SoC, under Mitsubishi's "Andromeda" framework fork of AOSP. The project's centre of gravity is Honda's USB software-update path: because the headunit accepts update files signed with the widely known AOSP test key, the project can build update packages the headunit will install, yielding arbitrary code execution on the unit. Licence: MIT (bundled AOSP-derived components remain Apache-2.0; Honda/Mitsubishi material is not relicensed).

## How it works

The toolchain is a monorepo of Python tools run on a host PC against official Honda update files. **apk-rebuilder** is the entry point: it extracts an official update file and post-processes it into smali code, repacked APKs and extracted ramdisk files — the precursors for analysing the headunit's apps. **aidl-rebuilder** parses the low-level smali to generate an authoritative list of AIDL interfaces, the IPC contracts by which Mitsubishi-authored apps and services talk to each other. **ota-builder** is the offensive counterpart: given an overlay directory, it builds Android update files that mimic authentic Honda USB updates — on a USB drive, the headunit reboots into recovery and applies the update. The enabler is Honda's trust decision: update files may be signed with the widely known AOSP test key (the repo bundles `signapk.jar` and the test key as AOSP-derived components), so a self-built package passes the signature check and executes. A fourth tool, apk-renderer, is a self-described "hacky", largely failed experiment kept for posterity. Alongside the tools, the `docs/` tree carries the hardware and system research: connector pinouts and board photographs, eMMC and SPI notes, GPIO, recovery-and-boot behaviour, the update mechanism, rooting, ADB, and HondaLink — the bench side documented as well as the software side.

## Where it fits

The section's Android-IVI worked example, and the cleanest demonstration in the KB of an IVI update path failing on key management rather than cryptography: the signature scheme works exactly as designed, but the trusted key is a public test key. It pairs with the section's other platform studies — [MMI3G-Toolkit](mmi3g-toolkit.md) (QNX/Harman, removable-media execution, its own signature-check failure) and [Q50 Reverse Engineering](q50-reverse-engineering.md) (Linux/Android, packaged-app install path) — the three together triangulating how 2010s IVI platforms handled code trust, and with [byd-dolphin-hacking](byd-dolphin-hacking.md) as the current-generation Android counterpart. Its concept link is [secure firmware updates](concepts/secure-firmware-updates.md): this is the consumer-IVI instance of the update-integrity failure class that page generalises. The AIDL/smali work also makes it a static-analysis reference for anyone meeting a Mitsubishi/Andromeda-derived unit.

## Limits and safety notes

Vehicle scope is the README's own: "most Honda Civics from 2016–2021, inclusive" — and lower-end trims such as the 2021 Civic LX are explicitly **not** supported, using completely different headunits. Per-trim verification of the update path beyond that "most" scoping is **not established**: the README offers no trim-by-trim test matrix. The README's legal notice is blunt and is carried here in substance: everything is experimental and at the user's own risk, with hard-bricked or soft-bricked headunits and units stuck in recovery/boot loops named as possible outcomes, and no guarantee anything works or is safe on the reader's hardware. The platform is end-of-life consumer electronics (2012-era SoC, Android 4.2.2), so the findings date with the hardware.
